# 긴 마크다운 문서 무중단 생성 및 에러 적응(Adaptive) 규칙 (requirements / design / tasks 등)

`requirements.md`, `design.md`, `tasks.md`, Implementation Plan 등 **긴 `.md`
문서**를 만들 때, 출력 토큰 한도로 인해 내용이 잘리거나 도구 호출이 실패하는
문제를 방지하기 위한 **강제 규칙**입니다. 기존 `markdown-rules.md`를 대체/보강
합니다. 아래 규칙은 **선택이 아니라 의무**입니다.

## 목차
1. 핵심 원칙 (왜 실패하는가)
2. 정량적 청크 상한선 (가장 중요)
3. 표준 작성 절차 (Outline → 청크 반복)
4. "끝까지 완료" 진행 추적 루프
5. 에러 대응 및 검증 (무한 청크 축소)
6. 도구 호출 무결성 (필수 파라미터 누락 금지)
7. 금지 사항 (Anti-patterns)
8. 실행 체크리스트

## 1. 핵심 원칙 (왜 실패하는가)

- 실패의 원인은 **한 번의 도구 호출(fs_write/fs_append)에 너무 많은 내용을 담기
  때문**입니다. "이 정도면 한 번에 되겠지"라는 판단이 곧 실패로 이어집니다.
- 따라서 **"적당히 나눈다"는 판단을 신뢰하지 않습니다.** 대신 아래의 **정량적
  상한선**을 기계적으로 지킵니다.
- **채팅에 전문을 먼저 출력하지 않습니다.** 채팅 출력 → 파일 저장은 같은 내용을
  두 번 생성하는 이중 작업이고, 그 과정에서도 잘림이 발생합니다. 처음부터 **작은
  청크로 파일에 직접** 기록합니다. (사용자가 "채팅으로 먼저 보여줘"라고 명시적으로
  요청한 경우에만 채팅 출력을 하되, 그때도 아래 청크 상한선을 그대로 적용합니다.)

## 2. 정량적 청크 상한선 (가장 중요)

**한 번의 `fs_write` 또는 `fs_append` 호출은 아래 상한선을 절대 넘기지 않습니다.**

- **최대 40줄** 또는 **최대 1,500자** 중 **먼저 도달하는 쪽**을 기본 상한으로 함
- 코드 블록/표가 포함되면 상한을 더 낮춰 **25\~30줄**로 끊음
- 한 청크가 상한을 넘길 것 같으면 **반드시 더 잘게 쪼갬**
- "남은 내용이 얼마 안 남았으니 한 번에 끝내자"는 판단 **금지** — 남은 양과 무관
  하게 항상 상한선을 지킴 (이것이 마지막 20%가 실패하는 주된 원인)

## 3. 표준 작성 절차 (Outline → 청크 반복)

1. **작성 전 계획 수립:** 문서에 들어갈 **모든 섹션 목록을 먼저 나열**하고, 각
   섹션을 몇 개의 청크로 쓸지 대략 정한다. (예: "총 6개 섹션, 예상 10개 청크")
2. **1단계 — Outline 생성:** `fs_write`로 **제목 + 목차(섹션 리스트)만** 담긴 파일을
   먼저 만든다. 이때 본문은 넣지 않는다.
3. **2단계 이후 — 청크 반복:** `fs_append`를 사용해 **한 번에 청크 하나씩만** 추가
   한다. 절대 여러 섹션을 한 호출에 몰아넣지 않는다.
4. **한 청크 = 하나의 하위 섹션**, 또는 긴 하위 섹션의 **일부**. 짧은 섹션이라도
   상한선 안에서만 합친다.
5. 문서가 **완전히 끝날 때까지** 3\~4단계를 반복한다.

## 4. "끝까지 완료" 진행 추적 루프

마지막 20%에서 멈추는 것을 막기 위해, **진행 상태를 명시적으로 추적**한다.

- 각 청크를 쓴 뒤, 내부적으로 **"작성 완료 섹션 / 남은 섹션"**을 갱신한다.
- **남은 섹션이 하나라도 있으면 멈추지 않고** 다음 `fs_append`를 계속 호출한다.
- "여기까지 하고 나머지는 다음에"라는 식의 **부분 종료 금지.** 사용자가 중단을
  요청하지 않는 한, **목차의 모든 항목이 채워질 때까지** 자동으로 이어서 진행한다.
- 여러 번의 도구 호출이 필요하더라도 그것이 정상이며, 호출 횟수를 아끼려고
  청크를 키우지 않는다.

## 5. 에러 대응 및 검증 (무한 청크 축소)

가장 중요한 에러 복구(Fallback) 규칙입니다. 도구 호출 중 에러가 발생하면 **내용의 크기가 여전히 너무 크다는 뜻**입니다.

- **적응형 청크 축소 (Adaptive Backoff):** `fs_append` 또는 `fs_write` 실행 중 에러가 발생하면, 즉시 직전에 시도했던 **청크 크기를 절반으로 줄여서 재시도**합니다.
  - 예: 40줄 작성 시도 중 에러 발생 → 20줄로 쪼개어 재시도.
- **연쇄 축소 (무한 쪼개기):** 크기를 줄였음에도 또 에러가 발생하면 **거기서 다시 절반을 줄입니다.** (20줄 → 10줄 → 5줄 → 2줄). 에러가 더 이상 발생하지 않고 정상 저장될 때까지 청크를 계속해서 잘게 쪼갭니다.
- **무결성 검증:** 문서를 다 쓴 뒤(또는 중간중간), **파일의 꼬리(tail)를 확인**해 마지막 청크가 잘리지 않고 온전히 저장됐는지 점검합니다. (예: `tail -n 20 파일명`)
- 마지막 줄이 문장 중간에서 끊겼거나 코드 블록/표가 닫히지 않았으면, **끊긴 지점부터 이어서** 다시 더 작은 크기의 `fs_append`로 보완합니다.

## 6. 도구 호출 무결성 (필수 파라미터 누락 금지)

청크 크기와 무관하게, **도구 호출 자체가 불완전하면 무조건 실패**합니다. 실제로
`fs_append`를 **`text`(추가할 내용) 없이 `path`만 넣어 호출**해 실패한 사례가
있었습니다. 이는 크기 문제가 아니라 **호출 구성 오류**이므로 Adaptive Backoff로도
해결되지 않습니다. 아래를 의무로 지킵니다.

- **`fs_append` 호출 시 `path`와 `text`를 반드시 함께 넣는다.** `text`가 비어 있거나
  누락된 호출은 절대 하지 않는다. (파일에 실제로 쓸 내용이 없으면 호출 자체를 하지
  않는다.)
- **`fs_write` 호출 시 `path`와 `text`를 반드시 함께 넣는다.** 빈 본문으로 호출하지
  않는다.
- **호출 직전 자기 점검:** 도구를 부르기 전에 "필수 파라미터가 모두 채워졌는가"를
  1초 확인한다. 특히 내용을 담는 파라미터(`text`)를 빠뜨리지 않았는지 본다.
- **같은 실패 2회 금지:** 필수 파라미터 누락으로 한 번 실패했다면, 재시도 시
  **반드시 누락된 파라미터를 채워** 호출한다. 동일한 형태로 재호출하지 않는다.
- 이 오류는 청크 축소로 해결되지 않는다. 크기를 줄이지 말고 **누락된 파라미터를
  채우는 것**으로 대응한다.

## 7. 금지 사항 (Anti-patterns)

- 🚫 전체 문서를 **단일 도구 호출**로 작성 (`fs_write` 한 번에 전문)
- 🚫 에러가 났을 때 동일한 양의 텍스트를 그대로 다시 시도하는 행위 (반드시 크기를 줄일 것)
- 🚫 "남은 내용이 조금이니 한 번에 마무리" — 상한선 초과의 주범
- 🚫 청크 상한선(40줄 / 1,500자)을 넘기는 append
- 🚫 채팅에 전문을 먼저 뿌린 뒤 그대로 복사해 저장 (이중 생성 → 잘림 위험)
- 🚫 목차 항목을 남겨둔 채 응답 종료 (부분 완료)
- 🚫 **`fs_append`/`fs_write`를 `text` 없이(빈 본문/파라미터 누락) 호출** — 호출 구성 오류
- 🚫 필수 파라미터 누락 오류를 **크기 축소로 대응** (원인은 크기가 아니라 누락)
- 🚫 동일한 누락 형태로 도구를 **그대로 재호출**

## 8. 실행 체크리스트

문서 생성 시 아래를 순서대로 지켰는지 확인한다.

- [ ] 작성 전 전체 섹션 목록과 예상 청크 수를 계획했는가
- [ ] `fs_write`로 제목 + 목차만 담은 파일을 먼저 만들었는가
- [ ] 이후 모든 추가는 `fs_append`이며, 각 호출이 40줄 / 1,500자 이하인가
- [ ] `fs_append`/`fs_write` 호출마다 `path`와 `text`를 **둘 다** 채웠는가 (빈 본문 금지)
- [ ] 에러 발생 시 즉시 청크 크기를 절반(1/2)으로 줄여가며 재시도했는가 (Adaptive Backoff)
- [ ] 코드/표 포함 청크는 25\~30줄로 더 잘게 끊었는가
- [ ] 목차의 모든 섹션이 채워질 때까지 멈추지 않고 이어갔는가
- [ ] 마지막에 tail을 확인해 잘림/미완결이 없음을 검증했는가
