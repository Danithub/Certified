# 서브에이전트 위임 실패 시 폴백 규칙

## 원칙
- 서브에이전트(invoke_sub_agent) 위임은 "가능하면 활용"하는 최적화 수단일 뿐,
  작업 진행의 필수 조건이 아니다.
- 위임 호출이 실패하거나 즉시 취소되면, 지체 없이 해당 작업을 **직접 수행**한다.
  사용자에게 다시 위임을 시도할지 되묻느라 진행을 멈추지 않는다.
- 단, "직접 수행"은 현재 세션에 **파일 쓰기·터미널 실행 도구가 있을 때만** 가능하다.
  도구가 없는 오케스트레이터 세션은 아래 "예외" 절을 따른다.

## 판단 기준
- 동일 세션에서 서브에이전트 호출이 **1회라도 즉시 취소/실패**하면,
  그 세션에서는 위임이 고장난 것으로 간주하고 이후 작업은 직접 처리한다.
- 페이로드(컨텍스트·프롬프트) 크기를 줄여도 취소가 반복되면,
  이는 입력 문제가 아니라 세션/환경의 실행 메커니즘 문제로 판단한다.

## 직접 수행 방식 (쓰기·실행 도구가 있는 세션)
- context-gatherer가 하던 일(코드 탐색·파일 분석·관련 위치 파악)은
  grep/find/read 등 파일 도구로 직접 조사한다.
- general-task-execution이 하던 일(구현·수정·검증)은
  현재 세션에서 직접 코드를 작성하고 검증한다.

## 사용자 안내
- 위임이 실패해 직접 수행으로 전환할 때는, 한 줄로 그 사실만 간단히 알린다.
  (예: "위임이 취소되어 직접 처리하겠습니다.")
- 반복적으로 실패하면, 근본 해결을 위해 새 세션/IDE 재시작을 함께 권고한다.

## 예외: 쓰기·실행 도구가 없는 오케스트레이터 세션 (전 작업 공통)

### 배경
- Kiro IDE 1.0 이후 spec 세션(문서 생성 및 "Run All Tasks" 실행 모두)은
  **오케스트레이터 모드**로 동작한다. 이 모드의 에이전트는
  태스크 상태 관리·읽기/검색·위임(invoke_sub_agent)만 가지며,
  **파일 쓰기(fs_write/str_replace/fs_append/delete_file)와 터미널 실행 도구가 없다.**
- 이 모드에서는 모든 산출물 작업을 서브에이전트에 위임한다:
  - spec 문서(requirements.md / design.md / tasks.md / bugfix.md) 생성·수정
  - 요구사항 상세화, 스펙 포맷(diagnostics) 수정
  - 앱 소스 코드 편집, 테스트 스크립트 작성·실행
- 따라서 위임이 끊기면 **작업 종류와 무관하게** "직접 수행"(생성·수정·검증)
  폴백을 이행할 수 없다. 위쪽 "직접 수행" 규칙은
  **쓰기·실행 도구가 실제로 있는 세션(일반 Vibe 등)에만 적용**된다.

### 세션 판별 (파일명이 아니라 도구로 판단)
- 현재 세션에 파일 쓰기 또는 터미널 실행 도구가 **없다면** 오케스트레이터
  세션으로 간주한다. (tasks.md 실행만의 문제가 아니다.)
- 이 경우 가능한 것은 조사(read/grep/list)까지이며,
  생산·수정·검증은 위임을 통해서만 가능하다.
- 이 판별은 워크플로 종류(Feature / Bugfix / Quick Spec)와 무관하게 동일하게
  적용된다. 셋 다 각 단계를 서브에이전트에 위임하므로 위임이 끊기면 똑같이 막힌다.

### 처리 순서
1. 위임 실패/취소 시, 현재 세션에 쓰기·실행 도구가 있는지 먼저 확인한다.
   - 있으면: 위쪽 "직접 수행" 폴백을 그대로 따른다.
   - 없으면(오케스트레이터): 아래 2~3으로 간다.
2. 위임을 **1회 재시도**한다(일시적 취소 대비).
3. 재시도도 실패하면 폴백을 포기하고,
   **새 세션(또는 일반 Vibe 세션) 전환을 권고**한다.

### 전환 권고 시 반드시 포함할 것 (필수)
"새 세션으로 넘어가세요"로 끝내지 말고, 사용자가 곧바로 복사해 쓸 수 있는
**"새 세션 시작 스크립트"**를 함께 제시한다. 스크립트에는 아래를 포함한다.
1. 무엇을 이어가는지: 대상 spec/파일 경로 + 이어갈 단계(문서 단계명 또는
   남은 태스크 번호)
2. 지금까지 완료된 것과 현재 상태(done / 남은 것)
3. 새 세션에 그대로 붙여 넣을 **시작 프롬프트 원문**
4. 어떤 세션으로 가야 하는지 명시:
   - 문서 생성/수정, 요구사항 상세화, 포맷 수정 → spec 세션에서
     해당 단계로 재진입(위임 복구 시) 또는 일반 세션에서 문서 직접 편집
   - 코드 편집·테스트 실행 등 실행이 필요한 작업 → 일반 Vibe 세션
     (파일 쓰기·node 등 실행 가능)
5. 재시도·재현을 위한 구체 명령(예: node 실행 경로, 검증용 조회 명령)이
   있으면 함께 적는다.

### 작업 유형별 시작 스크립트 가이드
- **spec 문서 단계(requirements/design/tasks/bugfix)**: 대상 spec 이름과
  "이 spec의 <단계> 문서를 이어서 작성/수정해줘"를 명시하고, 이미 합의된
  내용·미결 항목을 요약해 붙인다.
- **앱 소스 코드 수정**: 대상 파일 경로, 수정 지점(함수/앵커), 적용할 변경
  요지, 검증 방법(빌드/컴파일 유무)을 적는다.
- **테스트 작성·실행**: 테스트 파일 위치, 실행 명령(node 등), 기대 결과
  (PASS/FAIL 의미)를 적는다.

### 작업 유형별 시작 스크립트 가이드 (워크플로별 보강)
- **Quick Spec(fast-task) 파이프라인 중단 시**: 단계 순서
  (clarify → requirements → design → tasks → review) 중 어디서 멈췄는지와,
  **현재 실제로 존재하는 spec 파일 목록**을 적는다. silent 단계라 파일 유무로만
  진행 지점을 판별할 수 있기 때문이다. 재개 프롬프트에 "다음 단계는 <X>부터"를 명시.
- **Bugfix 워크플로 중단 시**:
  - 문서 단계면 bugfix.md → design.md → tasks.md 중 남은 단계를 적는다.
  - 태스크 실행 단계면, **Task 1(버그 조건 탐색 테스트)은 수정 전 FAIL이 정상
    (버그 존재 증명 = 성공)**이며, 수정 후 재실행에서 PASS로 바뀌어야 함을 명시한다.
    새 세션이 탐색 테스트의 FAIL을 실제 실패로 오해하지 않도록 하기 위함이다.
  - 보존(preservation) 테스트는 수정 전후 모두 PASS여야 함(회귀 없음)을 함께 적는다.
- **Feature 워크플로 중단 시**: Requirements-First / Design-First 중 어느 순서인지와
  (config의 workflowType 참조), 남은 문서 단계를 적는다.
